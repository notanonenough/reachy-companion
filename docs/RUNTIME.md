# Устройство runtime

Технические детали текущих подсистем. Канонические файлы запуска находятся в `deploy/current/`; наблюдаемые версии и ограничения — в [REVIEW.md](REVIEW.md).

## Изменение личности владельцем

Личность и принципы задаёт владелец. Модель и фоновые обновления могут менять
цель и память, но не применять изменения профиля. Модель может подготовить
локальное предложение `propose_character`; оно само не является GitHub PR.
Параметр `production.character_refresh_s` в старых
конфигурациях принимается для совместимости и больше не запускает пересмотр личности.

При остановленном runtime на узле, где хранится `production.state_path`, сначала
прочитайте текущую ревизию, затем выполните явную правку через существующий CLI:

```sh
python -m reachy_companion.autonomous.production inspect --state /path/to/state.sqlite3
python -m reachy_companion.autonomous.production set-character \
  --state /path/to/state.sqlite3 --expected 3 --reason 'Выбор владельца' \
  --personality 'Дружелюбный, непринуждённый и любопытный' \
  --principles 'Уважать личные границы'
```

В `--expected` укажите ревизию из `inspect`. Можно передать одно или оба поля,
каждое длиной от 1 до 512 символов; непереданное поле сохраняется. Причина обязательна.
Команда отказывает при устаревшей ревизии или работающем владельце runtime.
Следующий запуск сеанса прочитает сохранённый профиль. Эта правка не меняет
память и цель и не отменяет обязательные проверки STOP, privacy и разрешений.

### Предложение профиля через GitHub PR

Владелец просматривает локальные предложения и явно публикует выбранное:

```sh
python -m reachy_companion.autonomous.production list-character-proposals --state /path/to/state.sqlite3
python -m reachy_companion.autonomous.production publish-character-proposal PROPOSAL_ID \
  --state /path/to/state.sqlite3 --repo OWNER/REPOSITORY
```

На узле публикации нужен авторизованный `gh` с правом записи в выбранный
репозиторий и ветка `main`. Publisher создаёт настоящую ветку и PR с одним
JSON-файлом `proposals/character/PROPOSAL_ID.json`. В нём только ID, предлагаемые
поля и причина. Проверьте их перед публикацией: в публичном репозитории они
будут доступны всем. Текущий профиль, память, локальная ревизия и сведения
сеанса в PR не передаются. Runtime может продолжать работать во время публикации.

Автоматический ревьюер не назначается, автоматического слияния нет. Владелец
вручную сливает подходящий PR или закрывает его без слияния. Затем при
остановленном runtime явно применяет принятую версию:

```sh
python -m reachy_companion.autonomous.production apply-character-proposal PROPOSAL_ID \
  --state /path/to/state.sqlite3
```

Команда проверяет слияние, точный commit и содержимое PR. Изменённый в GitHub
текст нельзя применить как исходное предложение: подготовьте новое локальное
предложение и PR. Если владелец уже изменил затронутое поле профиля, старое
предложение отклоняется. Обновления памяти, цели и незатронутых полей сохраняются.
Подача и слияние PR сами по себе активный профиль не меняют.

После сетевой ошибки повторите публикацию с тем же ID и репозиторием: команда
сверяет существующую ветку и PR. Повторное применение уже принятого предложения
возвращает его ревизию без новой записи. Локально хранится до 128 предложений;
одинаковое предложение для той же исходной версии полей использует прежний ID.

## Запуск с MacBook

После установки на Mac доступны две команды из любого каталога:

```sh
reachy-on   # включить вычисления Mac и разговорный сеанс
reachy-off  # выключить сеанс, выгрузить все службы Mac и освободить память моделей
```

При включённом профиле движений `reachy-on` проверяет реальный режим приводов. Если они выключены, после получения разрешений нового аудиовладельца выполняется единственный штатный защищённый `wake`, до запуска автономного цикла. При неизвестном результате повторной команды движения нет; запуск отменяется. Статус активного сеанса с выключенными или неизвестными приводами — `degraded`, а не `ready`.

Автозапуск на Mac отключён. Конфигурации хранятся вне папки входа LaunchAgents:
`~/Library/Application Support/Reachy Companion/LaunchAgents`. `reachy-on` явно
включает и загружает задания; `reachy-off` выгружает и отключает их, проверяя также
завершение дочерних процессов. `KeepAlive` действует только во время ручного запуска.
При недоступности устройств `reachy-off` всё равно выключает вычисления Mac и
сообщает, что удалённая остановка не подтверждена. Базовые службы hub и Reachy
остаются включёнными, с запуском при загрузке устройств.

Пока работает Mac gateway, его обёртка держит `caffeinate -i`: автоматический сон
от бездействия не обрывает вычисления и доставку S3. Assertion привязан к процессу
gateway и снимается при его завершении; глобальные настройки питания не меняются.
Закрытие крышки и явный сон не блокируются. При потере Mac hub штатно завершает
сеанс, после возвращения компьютера нужен `reachy-on`.

Для установленной связки MacBook → hub → Reachy используются приватные
`config.mac.local.json`, `config.autonomous.mac.local.json` и файлы в `secrets/`.
Mac запускает llama, gateway, Whisper и Piper через LaunchAgents `local.reachy.*`;
hub — `reachy-production.service`, робот — `reachy-production-audio.service`.
На роботе остаётся единственный владелец микрофона и PCM-выхода.
Основные ответы формирует локальная Qwen3.5 9B Q4_K_M из GGUF; отдельная 0,8B выбирает маршруты и
передаёт готовый ответ. У маршрутизатора отключена прямая речь. Личные фоновые
размышления основной модели используют отдельное структурированное решение о необходимости
речи и не считаются словами человека. `models.main.structured_reply=true`
ограничивает обычный ответ единственным полем `response`; в TTS передаётся
только его текст. Фоновая память получает отдельный JSON patch и отсчитывает
следующий интервал после завершения обновления. Отмена текущей речи при новом
фрагменте не отзывает неизменившееся разрешение микрофона. При постоянном шуме речевой фрагмент
передаётся в STT максимум через четыре секунды, без бесконечного ожидания тишины.
Контекст основной модели сериализуется компактно; стабильное состояние идёт
перед меняющейся репликой, без удаления полей. В текущем LaunchAgent основной
модели лимит RAM-кэша промптов — 512 MiB: прежних 128 MiB не хватало на состояние
одного запроса. Это не устраняет задержку распознавания и обработки контекста;
скорость полного живого ответа нужно измерять отдельно.

```sh
scripts/production-control start
scripts/production-control status
scripts/production-control stop
```

Это служебные команды: `stop` останавливает только сеанс, сохраняя модели в памяти.
Для полного выключения используется `reachy-off` (или `production-control shutdown`).

`start` сначала проверяет готовность моделей, затем выдаёт новый аудиосеанс.
`stop` останавливает сеанс и выключает его микрофон; модели остаются загруженными.
После STOP, потери прав или неизвестного результата вывода нужен явный новый
`start`: автоматического повторного включения микрофона нет. Логи Mac находятся
в `data/mac-runtime/`, отчёты hub и робота — в их `data/production-*/`.
Обновление разрешений речи читает `/operator` с HTTP-тайм-аутом 100 мс и пределом
ответа 8 KiB вместо общего 10-секундного ожидания. Задержавшееся чтение освобождает
свой слот для следующей штатной проверки; срок действительности разрешения
остаётся 300 мс, просроченные ответы не принимаются.

На Apple Silicon нужны Python 3.13, extras `worker,autonomous` и нативный `sox`
в PATH LaunchAgent. Для macOS используется Vosk 0.3.44; Whisper medium работает на CPU
с `int8`; для этого профиля `production.stt_deadline_s=8` ограничивает ожидание
распознавания, не меняя короткие сроки разрешений на микрофон и движения. Piper работает через ONNX Runtime. Проверяются SHA256 весов и полнота кэша
Whisper, включая поддерживаемые CTranslate2 варианты `vocabulary.json` и
`vocabulary.txt`. Модели llama слушают loopback; вычисления доступны hub через SSH.
Для аудиоканала разрешены только адрес hub и аутентифицированный локальный
протокол с отдельной остановкой и одноразовыми UDP challenges.
При потере ответа production делает до двух повторов с новым challenge в одном
окне не более 240 мс. Перед отправкой hello, renewal и принятием ответа заново
проверяется разрешение владельца и свежий прогресс основного цикла. Срок lease
на роботе остаётся 300 мс, challenge — 100 мс; завершённый сеанс не возобновляется
автоматически. Это помогает пережить потерю двух ответов, но не длительный обрыв Wi-Fi.
На hub и Reachy отключено Wi-Fi power save. Профили Wi-Fi закреплены за
текущим BSSID, чтобы фоновое сканирование точек доступа не прерывало короткие
разрешения аудиосеанса; перед сменой точки доступа эту привязку нужно обновить.
В текущей установке hub (`192.168.0.186`) и Reachy (`192.168.0.184`)
подключены к LinkedList на 5 ГГц; Ethernet на hub отключён, кабель не требуется.
LinkedList на 2,4 ГГц
сохранён, но этот диапазон давал провалы до 300 мс даже с проводным hub.
Mac остаётся на Vuqar 5G; SSH-алиасы устройств используют ProxyJump через
`reachy-router-vuqar`, включая соединения с вычислительными службами Mac.
MTU Wi-Fi Mac и внешнего интерфейса Xiaomi — 1492 по ограничению сети Vuqar.
Опрос статуса и аудионаблюдений использует два отдельных постоянных HTTP-соединения,
чтобы не занимать ограниченные слоты сервера частыми переподключениями.
Профиль `actuators=bounded_stock` подключает автономные плавные повороты головы
и антенн через существующий штатный daemon и `Hub.expression`. Используются
текущие разрешения оператора, ограниченные планы и наблюдение завершения
собственного UUID; подтверждение физической позы и жёсткого срока остановки
этот транспорт не даёт. Новые движения блокируются при неизвестном результате.
Явный `start` после `WITHDRAWN` закрывает старый сеанс и создаёт новый.
Известная остановка USB PCM без доступного frozen cursor завершает только
отменённый поток; курсор остаётся неизвестным, возобновление такого потока
запрещено. Полное воспроизведение по-прежнему требует измеренных аудиокадров.

Панель `/control` позволяет отдельно разрешить или запретить движения и доступ
Ричи к кадрам камеры. Разрешение на движение само не запускает поворот или
автономный сеанс. Включение проверяет актуальное состояние и не забирает
управление у другого владельца. Запрет доступен и во время сеанса.
Доступ к камере сохраняется в `data/camera-state.json`, при отсутствии или
повреждении настройки кадры запрещены. Закрытие доступа блокирует новые кадры
непрерывного сенсора и разовых снимков; смена поколения исключает повторную
выдачу старого кадра. Кэш распознавания очищается при следующем фоновом опросе.
СТОП также закрывает доступ к камере и запрещает новые движения. Эти кнопки
не отключают питание камеры или приводов и не останавливают видеопоток
штатного daemon. После установки новой настройки доступ к камере закрыт,
разрешение пользователь даёт отдельной кнопкой.

В профиле непрерывного прототипа камера подключается через
`reachy-camera-sensor.service`: численные яркость и изменение кадра поступают
в кэш дважды в секунду. Измерения получаются из существующего Unix socket
штатного daemon, без нового владельца камеры, микрофона или приводов.
TTL 1,5 секунды относится к получению кадра; возраст физической экспозиции
остаётся неизвестным. Privacy, quiet и завершение аудиосеанса закрывают чтение
и очищают кэш. Изображения не сохраняются.

На Mac отдельная **SmolVLM2-500M Q8** описывает объекты и их положение в кадре.
Штатная служба камеры выдаёт один JPEG 640×360 по аутентифицированному `/frame`;
существующий SSH-туннель доставляет его только на Mac. Два фоновых потока gateway
независимо обновляют кадр и выполняют VLM-запрос. В работе один запрос и максимум
один ожидающий кадр, который заменяется более новым. При смене сеанса, privacy,
потере источника или истечении TTL поздние результаты не принимаются.
При HTTP-тайм-ауте новый inference не запускается до подтверждения свободного
слота отдельного VLM-сервера.

`camera.scene` получает описание из мгновенного `/vision`-кэша дважды в секунду.
TTL описания — 20 секунд от получения исходного кадра, включая время inference;
возраст экспозиции не считается известным. Описание помечено как вывод VLM и
может содержать ошибки. Пока картинка обрабатывается, основной цикл LLM, речь
и движения продолжаются. В `gateway /health` доступны задержка VLM, занятость,
счётчики результатов и число ожидающих кадров, без самих изображений.

`camera.change` получает из `/vision/change` подтверждённые появления людей и
предметов. Отдельный **YOLOX-s** на Mac возвращает до шести объектов из 80 категорий
COCO с сектором `left/center/right`, вычисленным по центру рамки в изображении.
Это категории и количество, не идентификация людей или
надёжный трекинг одинаковых предметов. Первые два наблюдения задают фон комнаты,
новое появление подтверждается двумя последующими наблюдениями. Изменение сектора
само по себе не создаёт событие. Три пропуска снимают присутствие, повторное
появление той же категории/числа имеет паузу 60 секунд.
Детектор работает в отдельной фоновой линии ONNX Runtime,
одним активным и одним заменяемым ожидающим кадром; между обработками пауза
0,25 секунды. Порог score — 0,65, подавление перекрывающихся рамок — IoU 0,5.
`camera.objects` содержит текущие обнаружения, TTL 3 секунды. Полный разбор сцены
VLM продолжается независимо. Задержки детектора доступны в `health.vision.detector`.
Веса [OpenCV Zoo YOLOX-s](https://github.com/opencv/opencv_zoo/tree/main/models/object_detection_yolox)
проверяются по опубликованному SHA256; URL, hash и Apache-2.0 license хранятся в
`models/yolox/`. Зависимости Mac: extra `vision` из `pyproject.toml`.

Свежий визуальный повод входит в следующий быстрый запрос без обращения человека.
Модель может одновременно выбрать `attentive` и запустить фоновую оценку
комментария. Для stock-контроллера такой жест становится ограниченным поворотом
на 8° в нужную сторону с возвратом в нейтраль; сектор центра означает нейтраль.
Занятость основной модели не блокирует независимо разрешённый жест. Сектор
фиксируется в снимке быстрого запроса и проверяется повторно перед предложением
движения. Это грубое направление, не наведение точно на пиксель.

На событие предлагается один жест и одна оценка комментария; между оценками
речи минимум 45 секунд, текущий разговор имеет приоритет. Основная модель может
выбрать молчание. Событие живёт максимум 30 секунд и требует свежих подтверждений
присутствия; исчезновение, устаревание, смена владельца или privacy отменяют
ожидающие визуальные ответы. Время реакции включает два обнаружения, следующий
быстрый LLM-запрос и доступность существующего моторного cooldown; ждать VLM
или окончания основной модели для поворота не требуется.

При `motion.follow_person=true` (только `bounded_stock`) короткие жесты заменяются
фоновым слежением головы **и корпуса**, без автоматического возврата в центр.
`camera.person` получает нормированные рамки до трёх людей из `/vision/person`,
TTL 3 секунды, с идентификатором источника и номером кадра. Для слежения порог
детектора снижен до 0,45, требуется два последовательных наблюдения; события
появления для комментариев сохраняют порог 0,65. Детектор теперь обрабатывает
кадры с паузой 0,25 секунды между вычислениями и latest-only очередь.
`gateway.vision.detector_backend=auto` выбирает на Mac Core ML с
`CPUAndNeuralEngine`, без использования GPU детектором; на других платформах —
один CPU-поток. Значения `cpu` и `coreml` позволяют явно выбрать backend.
Компиляция Core ML прогревается на искусственном кадре; кэш содержит только
модель. При ошибке ускорителя режим `auto` переходит на CPU в том же рабочем
слоте, а `health.vision.detector.device/backend_error` и production status
показывают этот переход. Raw-кадры не сохраняются.
[Настройки Core ML](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html).
Лицо не обязательно, но далёкий затылок/частично закрытый силуэт может не распознаться.
Если на полном кадре человека нет, детектор проверяет до двух перекрывающихся
увеличенных боковых областей. Координаты переводятся обратно в полный кадр;
это тот же последовательный фоновый слот, а не дополнительные параллельные модели.

Контроллер предпочитает ранее выбранную ближайшую рамку, без распознавания личности.
Каждый шаг использует текущую измеренную позу и новый кадр, полученный после
предыдущего движения. Цель плавно обновляется относительно последней принятой
команды: небольшое расхождение измеренной и заданной позы не останавливает обзор.
Дополнительная проверка по фактической позе ограничивает накопление коррекции.
Все HTTP-вызовы и ожидание конечного движения выполняются
в фоновой задаче, быстрые LLM-запросы продолжаются независимо. Между задачами нет
очереди старых координат. Внутри одного шага проверки штатного драйвера используют
одно HTTP-соединение; каждое состояние считывается заново, команды при обрыве
соединения не повторяются. Соединение закрывается при завершении задачи.
При потере цели позиция сохраняется. При отсутствии
человека примерно 45 секунд робот осматривается: слева 45°, справа −45°, центр,
с остановкой на 6 секунд для VLM. Первый осмотр начинается через 5 секунд
после появления камеры. Разговор откладывает осмотр; обнаружение человека
немедленно переводит следующие шаги в слежение.

При слежении коррекция закрывает 85% оценённой горизонтальной ошибки, до 10°
головы и 8° корпуса за шаг; возле цели уменьшается. Длительность `minjerk`
адаптивная: от 0,35 секунды, со средней скоростью до 26°/с головы и 20°/с корпуса
по измеренной позе. Пиковое ускорение профиля ограничено 320°/с² головы,
250°/с² корпуса и 160°/с² наклона. Независимая проверка ограничивает скорость
и ускорение перед отправкой с небольшим запасом на шум измеренной позы.
У границы зоны покоя коррекция нарастает плавно (`smoothstep`), чтобы шум
координат не включал поворот скачком. Крупный шаг 10°/8° занимает около 0,43 с
вместо 0,57 с; это время движения, без задержек камеры и сетевых проверок.
Обзор сохраняет медленные шаги по 0,8 секунды. Зона покоя подавляет мелкую дрожь.
Абсолютные пределы: голова ±60°,
корпус ±50°, наклон головы ±10°, разность головы и корпуса ≤15°.
В штатном Hub добавлена отдельная внутренняя проверка таких шагов по измеренной
позе; обычный внешний expression по-прежнему не может задавать корпус.
Privacy, quiet, STOP, смена разрешений и перегрузка отзывают допуск; продолжать
движение по просроченным координатам запрещено. Статус содержит `tracking_mode`,
`tracking_error` и число осмотров. Завершение штатного UUID остаётся подтверждением
окончания команды, а не сертификатом точности физической позы.
Если измеренная поза выходит за допустимую область, слежение фиксирует `pose_fault`
и прекращает повторные попытки. Основной цикл и зрение продолжают работать;
`production-control status` показывает неисправность. После устранения причины
нужен явный перезапуск сеанса.

VLM запускается отдельным `local.reachy.vlm` на **двух CPU-потоках с низким
приоритетом**, без GPU offload модели и проектора. `reachy-on` загружает её,
`reachy-off` выгружает вместе с остальными вычислениями. Настройки находятся в
`gateway.vision`; установщик — `deploy/production/install_vision.py`.
Веса и проектор из [официального GGUF-репозитория ggml-org](https://huggingface.co/ggml-org/SmolVLM2-500M-Video-Instruct-GGUF)
проверены по SHA256; manifest лежит рядом с ними в `models/smolvlm2-500m/`.

Логи идут из устойчивой очереди SQLite на hub через существующий SSH-туннель
в аутентифицированный `PUT /logs/{id}` Mac gateway, затем в Yandex Object Storage
`reachy-s3/reachy/events/`. Ключи остаются в файлах `secrets/` на Mac. Gateway
принимает только метаданные событий (вид, время, идентификаторы и класс действия),
подтверждая доставку после успешного S3 PUT; речь, кадры и рассуждения не экспортируются.
Доставка группирует до 32 событий в объект с полем `events`, сохраняя ID каждого
события; подтверждение всей группы применяется одной транзакцией. Повторная
попытка той же группы использует тот же ключ объекта. VPS и получение обновлений с VPS
отключены. Новые записи не ждут отключённых получателей; ранее накопленные
неотправленные записи сохраняются. Для подключения служит
`deploy/production/install_continuous.py`; он сохраняет резервные копии настроек
и требует явного перезапуска через `scripts/production-control restart`.

При перегрузке новые запросы контекста приостанавливаются вместе с обычными
реакциями. Готовые ответы и обращения, поступившие за время ожидания, сохраняются
для следующего решения с исходными ограничениями срока действия и полномочий.
Опросы датчиков продолжаются и во время разгрузки: каждый источник сохраняет
один занятый слот, TTL и проверку privacy/владельца. Свежий опрос камеры не мешает
возобновлению; превысивший порог читатель остаётся учтён до фактического завершения.
`runtime.pressure` показывает причину перехода, возраст активных задач, очередь,
порог и длительность разгрузки; последняя причина сохраняется после восстановления.
На время DRAINING/CONSOLIDATING новое STT не запускается. Уже выполняющееся
распознавание завершается, измерение уровня звука продолжается, а один ожидающий
фрагмент заменяется более свежим. После восстановления исходные TTL и разрешения
проверяются заново. `audio.processing_paused` отличает эту паузу от выключения
микрофона; просроченный или отозванный фрагмент не возобновляется.

`network` обновляется результатами уже существующих HTTP-проверок хаба к роботу
и Mac, без новых сетевых запросов. TTL — 1,5 секунды; каждый адрес независимо
помечается reachable/failed/stale/unknown. Измеренное время включает обслуживание
HTTP и ожидание планировщика, поэтому это не ICMP ping. Доступность Интернета
остаётся unknown. Те же численные измерения доступны в `runtime.network`
и кратком `production-control status`. Статус датчиков теперь включает также
звук и неподключённую телеметрию, не раскрывая содержимое речи или кадров.

Для Reachy daemon 1.2.11 сохранён патч
`deploy/patches/factory-live-status.patch`, обновляющий фактические ready/last_alive
в REST-телеметрии; прежний файл на устройстве сохранён рядом с суффиксом
`.before-mac-live-status`.

На роботе установлен `reachy-mini-motor-controller==1.5.6` (CPython 3.12,
aarch64); API типов совпадает с ранее установленным 1.5.4. Версия 1.5.5
исправляет зависание `async_read_raw_bytes`, а 1.5.6 ограничивает накопление
статистики моторного цикла:
[официальный changelog](https://github.com/pollen-robotics/reachy-mini-motor-controller/blob/main/Changelog.md).
Обновлён только этот пакет, без зависимостей и без замены локальных патчей daemon.
Wheel обеих версий, SHA256-манифесты и архив прежней установки сохранены на роботе
в `/home/pollen/reachy-companion/backups/motor-controller-20261102/`.
Для отката сначала остановить production и daemon, установить сохранённый wheel
1.5.4 через `/venvs/mini_daemon/bin/python -m pip install --no-deps --no-index`,
затем запустить daemon и явно открыть новый сеанс через `production-control start`.
Установка исправления сама по себе не подтверждает долговременную стабильность.

### Диагностика и восстановление production

STT использует один удалённый слот: `/transcribe/reserve` выдаёт билет текущего
worker, `/transcribe` запускает только этот билет, а `/transcribe/settle`
отзывает ещё не начатый запрос или ждёт завершения уже запущенного. После
HTTP-таймаута поток hub остаётся занят до подтверждённого завершения Whisper;
новая запись заменяет только ожидающий элемент, не создавая очередь HTTP-запросов.
Просроченный результат не превращается в реплику. Статус
`audio.waiting_terminal` явно показывает ожидание, а `health.transcription`
на worker — реальную занятость. Старые билеты не допускаются повторно;
смена boot worker не считается доказательством завершения прежней операции.
Legacy `/transcribe` остаётся доступным, но при занятом слоте отвечает 409.

```sh
scripts/production-control status         # единый статус вычислений, узлов и сеанса
scripts/production-control status --json  # подробная диагностика без текста реплик
scripts/production-control restart        # явное закрытие старого и создание нового сеанса
scripts/diagnose-conversation             # STT на искусственной тишине, без воспроизведения
scripts/diagnose-conversation --wav /absolute/path/question-16khz.wav
```

`ready` означает готовые вычисления, активные службы и готовый аудиосеанс.
`degraded` показывает работающий сеанс с проблемами; `needs_start` — остановку,
требующую явного запуска; `stopped` — выключенный сеанс; `unavailable` — отсутствие
достоверного статуса. Причины и команда восстановления входят в статус. Последний
завершённый отчёт не подменяет текущую готовность. Недоступность камеры и внешней
доставки отражается в возможностях. Счётчики STT разделяют пустое распознавание,
ошибки, тайм-ауты, устаревшие и заменённые фрагменты. Последние 32 результата
содержат lineage ID, задержки и продолжительность аудио, без текста.
`production.stt_diagnostics=true` дополнительно запрашивает причины фильтрации worker;
для этого на worker требуется `conversation.recognition.diagnostics_enabled=true`.

Проверка здоровья вычислений использует HTTP-тайм-аут не более секунды. В production
`production.compute_health_timeout_s` (по умолчанию 3 секунды, пределы 0,5–10)
разрешает краткие ошибки транспорта только с прежним compute boot ID. Смена владельца,
карантин или отзыв авторизации завершают сеанс; сроки разрешений оператора и аудио
не увеличены. Новые фоновые обновления памяти откладываются на
`production.maintenance_idle_s` после распознанной реплики (по умолчанию 10 секунд).
Самостоятельное размышление откладывается на 30 секунд. Уже выполняющийся запрос
продолжает занимать свой слот до фактического завершения.

### Воспроизводимая установка

Текущая установка описана в [DEPLOYMENT.md](DEPLOYMENT.md) и `deploy/current/`.
Старые `install_maintenance.py`, `install_continuous.py`, `install_vision.py` были
пошаговыми миграциями существующей установки; для нового развёртывания они не используются.

Firewall хранит единственный набор правил для точного
`security.robot.production_peer_ipv4`; старт аудиосервиса больше не меняет правила.
Изменение применяется атомарно к собственной таблице, с 90-секундным откатом.
После проверки **нового** SSH-соединения и доступа hub нужно остановить напечатанный
rollback timer. Повторное применение не накапливает правила. Для смены сети нужно
обновить IP в настройках установки.

Отправка журналов в S3 повторно использует HTTPS-соединение. При транспортном
сбое допускается одна повторная запись с тем же ключом объекта и содержимым;
очередь подтверждается только после успешного ответа. Локальный S3 relay
ожидает до 12 секунд, чтобы вместить этот повтор. Отправка остаётся фоновой,
сроки разрешений аудио и движений от этого не меняются.

Модель заранее размещается в `models/`; `--main-model` переключает путь в plist.
При смене модели также согласуются alias, `models.main.id`, `llm.model`
и аудит фактических весов, токенизатора, шаблона и размера контекста. Рабочая 9B
использует alias `reachy-main9b`, контекст 8192 и temperature 0.2.
Whisper medium работает с `beam_size=1`: на восьми синтетических русских
записях с шумом и без него слова совпали с beam 5, медиана уменьшилась с 2.11 до 1.89 с.
Для аудио до 8 секунд декодер ограничен `max(32, 16 + ceil(20 * seconds))`
новыми токенами. Это ограничение вычисления, а не обрезка готового текста.
При исчерпании лимита или отсутствии завершающей временной метки результат
целиком отбрасывается, включая уже распознанное начало. Диагностика отмечает
`decoder_budget_exceeded`; длинные записи старого API сохраняют прежний режим.
Это устраняет зависимость запуска от доступа к Downloads. `--vad-filter` включает
встроенный VAD Whisper в Mac-профиле; `--no-vad-filter` выключает его. В текущей
установке VAD проверен на цифровой тишине и тестовой речи трёх уровней громкости.
Живая акустическая приёмка остаётся отдельной проверкой.

На Mac LaunchAgents используют `reachy_companion.production_logs`: каждый поток
stdout/stderr ограничен 5 MiB плюс три резервных файла, права логов — 0600.
После установки plist нужно перезагрузить соответствующий LaunchAgent.
Диагностика Whisper пишет числовые признаки и длину текста; текст сегмента не пишет.
Отдельная настройка `logging.log_transcripts` остаётся явным разрешением текстовых
логов старого voice API; эксплуатационный установщик выставляет её в `false`.
Production выводит в журнал краткое завершение, а полный
отчёт сохраняет в каталоге сеанса. Службы ограничивают поток записей в journal.

`reachy-report-retention.timer` ежедневно удаляет завершённые отчёты старше 7 дней
или сверх последних 30; отчёты младше часа, незавершённые каталоги и посторонние
файлы защищены от удаления. До применения можно проверить список:

```sh
.venv/bin/python -m reachy_companion.production_logs prune --data data
```

В статусе очередь различает локальное хранение и ожидающие отправки записи.
Заполненный локальный буфер при выключенном экспорте не выдаётся за сбой доставки.

При остановке hub сначала отправляет отдельный STOP роботу, затем закрывает
локальные задачи. Робот ожидает фактического выхода HTTP-обработчиков после закрытия
слушателей; незавершённый обработчик остаётся видимым. `cleanup_issues` и
`motion_after` объясняют неподтверждённую очистку, даже если обычных исключений нет.
Штатный транспорт движений по-прежнему не подтверждает физическую позу и аппаратный
срок STOP. При прерывании жеста возможен неизвестный результат: он блокирует новые
движения в этом сеансе и отображается как `motion:unknown_completion`.

Передача микрофона внешнему production-владельцу также освобождает старую полосу
жестов voice-agent: нейтральные и речевые анимации не запускаются параллельно с
production-движениями. Повторное обслуживание паузы не меняет expression version.
