# VOICE-COMPARE-01: предварительно зафиксированный план

Refs #46. Это сравнение двух уже установленных моделей на синтетических
репликах. Производственный конфиг, модель диалога, устройства и службы не
меняются. Запуск требует отдельного тихого окна ведущего после завершения
работ исполнителя #30. До этого разрешены подготовка и проверки без inference.

## Набор и критерии до запуска

`tests/fixtures/voice_compare/cases.json` содержит 12 независимых случаев:
арифметика, продолжение разговора, память, неизвестный говорящий, устаревшая
камера и ложная инструкция внутри данных — по два случая. Весь контекст
синтетический; сохранённых пользовательских prompts/profile в нём нет.
Пара получает одинаковый полный `companion-1`, включая политику персонажа.
Каждый случай имеет hash входа и rubric. Набор нельзя править после просмотра
ответов. Любая необходимая правка образует новый опыт, старые ошибки сохраняются.

Проверяются отдельно: JSON с единственным непустым `response` до 512 символов,
правильность задачи, русский язык (кроме запрошенных чисел), grounding,
неопределённость говорящего и отсутствие превращения цитаты в инструкцию.
Для арифметики/части follow-up ожидается точный ответ. Остальное оценивают
автор и независимый reviewer по опубликованному rubric с сохранёнными ответами.
Ошибка identity/grounding/injection не скрывается средним процентом качества.
Timeout, invalid JSON, пустой ответ и незавершённая генерация остаются в
знаменателе 12. Автоматических повторов нет.

## Сопоставимость и расходы

Обе модели вызываются как **main** через существующий `ModelBackend.generate`:
тот же `COMPANION_SYSTEM`, structured-response suffix, два точных tokenizer
вызова, native completion и validation. Маленькая модель не получает политику
fast lane. Шаблон сообщений одинаков; hashes весов/tokenizer для каждой
модели отдельные. Используются Qwen3.5-9B-Q4_K_M и Qwen3.5-0.8B-Q8_0,
пинованный llama b11941 / 19ff817fb. Различается и квантование, поэтому
результат сравнивает именно эти два установленных артефакта, не чистый эффект
размера модели.

Изолированные последовательные процессы `llama serve`, loopback 18941/18942,
контекст 8192, concurrency 1, GPU layers 99, reasoning off. Общие параметры
клиента: output cap 256, reserve 256, input cap 3000, template cap 256,
temperature 0.2, seed 1729. Для сравнения uncached input устанавливается
`cache_prompt=false` в измерительном transport adapter; штатный код gateway
не меняется. Это не измерение production cache hit-rate. Server cache RAM 512
для обеих моделей. Параметры, server argv и идентичность артефактов сохраняются.

Два блока в порядке 9B, затем 0.8B, одинаковый порядок 12 случаев в каждом.
Одна одинаковая опубликованная warmup-реплика перед каждым блоком (не входит
в 12): «Ответь одним словом: готов.», всего **26 completion calls maximum**,
без повторных inference.
Первый запрос и загрузка выделяются отдельно; 12 последующих запросов
измеряют прогретый процесс без повторного использования prompt cache.
Порядок блоков — ограничение: тепловое состояние/OS cache не контролируются
этим малым опытом. Model load/readiness ≤90s, HTTP call ≤30s; общий watchdog
≤15 минут. При unknown transport outcome блок прекращается, неначатые случаи
остаются `not_run`; следующий запрос в тот же процесс не отправляется.

Каждый процесс принадлежит runner через его `Popen` handle. В `finally`
terminate→bounded wait→kill только этого дочернего процесса, затем wait/exit
receipt. Никаких service start/stop, pkill, владельца робота или фонового
daemon. Занятый порт до запуска — отказ; HTTP только на собственном порту,
после проверки живого child. Перед блоком и после завершения фиксируется
владение listener, а не только совпадение номера порта.

## Evidence и решение

Сохраняются synthetic input/output, raw bounded native receipt, полный client
interval, same-call stage durations, input/output token counts, format/error
outcomes, запуск/known exit и hashes. Результаты всех 12 пар видны отдельно;
median/min/max относятся к этой малой выборке, не к p99 или гарантированному
времени ответа. Token counts не оцениваются по байтам.

Время здесь — main client/tokenizer/completion/validation, **не** весь путь
STT→ответ→TTS и не ear latency. Реальная сессия имела 2.262s ожидания финального
STT, 2.642s его работы и другие scheduler/TTS интервалы; более быстрая main
модель сама по себе не убирает их. Решение о смене модели принимает владелец
после отчёта, качества и ограничений; этот опыт ничего автоматически не
переключает.

## Команды до и после назначения окна

Подготовка без процессов и сети:

```sh
PYTHONPATH=src .venv-review/bin/python deploy/autonomous/voice_model_compare.py
PYTHONPATH=src:tests .venv-review/bin/python -m unittest test_voice_model_compare -q
```

Рабочая копия использует interpreter общей `.venv-review`; в чистом checkout
эти команды предполагают установленную среду проекта. Dry-run проверяет
hashes синтетических случаев и схемы; семь тестов отдельно запрещают сетевые
вызовы/процессы в dry-run, проверяют одинаковые настройки, потерю ownership
и cleanup после ошибки. Измерительный клиент дополнительно проверяет owner
listener перед каждым RPC; стоимость этой проверки включена в `client_s`
и отдельно указана в `included_ownership_check_s`. Это overhead измерителя,
а не native model computation. `handler_to_pre_serialize` здесь отсутствует:
используется локальный `Gateway.generate`, без дополнительного HTTP gateway.

После отдельного разрешения ведущего, из собственной рабочей копии:

```sh
/Users/notanonenough/workspaces/reachy-companion/.venv-review/bin/python \
  deploy/autonomous/voice_model_compare.py --execute \
  --installed-root /Users/notanonenough/workspaces/reachy-companion \
  --output /Users/notanonenough/reachy-release-backups/20261127-voice-compare-001
```

Каталог должен отсутствовать. Прерывание Ctrl-C проходит через тот же
`finally`, останавливающий и reap-ящий только собственный процесс. `known_exit`
в owner receipt обязателен; отсутствующая пара остаётся `not_run`, не успехом.
